# Сроки жизни токенов и переподключение интеграций

> Зачем: токены не вечные. Если первым об отвалившейся интеграции узнаёт клиент («агент сломался»), поставка выглядит плохо.
>
> Правила:
> - для каждой интеграции заранее знаем, когда и почему отвалится её токен;
> - ловим это проверкой до клиента;
> - переподключение — короткий описанный сценарий.
>
> Проверено на эталоне 09.11.2026: Google-токен умер на 7-й день, утренняя сводка вышла без календаря.

## Таблица

| Интеграция | Чем подключена | Сколько живёт | Что его убивает | Как переподключить |
|---|---|---|---|---|
| Google (Календарь, Почта, Диск, Таблицы) | OAuth: `~/.hermes/google_token.json` + `google_client_secret.json` | **Testing: 7 дней.** Production: бессрочно | см. ниже | авторизация заново в браузере (раздел «Google» ниже) |
| Todoist | личный API-ключ в `MCP_TODOIST_API_KEY` (заголовок MCP `ai.todoist.net/mcp`) | бессрочно | клиент сбросил ключ в настройках; удалил аккаунт | Todoist → Настройки → Интеграции → Для разработчиков → новый ключ в `.env`, перезапуск gateway |
| VK (канал) | ключ сообщества `VK_GROUP_TOKEN` | бессрочно | ключ удалили или пересоздали в «Работа с API»; бота сняли с админов; сообщество заблокировали | Управление сообществом → Работа с API → новый ключ (сообщения, управление) в `.env`, перезапуск gateway |
| Timeweb AI (основная модель) | API-ключ `TIMEWEB_API_KEY` | бессрочно, если не задан срок при выпуске | **кончился баланс**, ключ отозвали | пополнить баланс; новый ключ в `.env` |
| reg.cloud (запасная модель) | API-ключ `REGCLOUD_API_KEY` | бессрочно | баланс, отзыв ключа | то же |

Что убивает Google-токен:
- приложение в режиме Testing — 7 дней;
- клиент отозвал доступ на myaccount.google.com/permissions;
- токеном не пользовались 6 месяцев;
- смена пароля (для scope Gmail);
- больше 100 refresh-токенов на один client_id у аккаунта.

Самый частый реальный сбой у API-ключей — **деньги, а не токен**: пустой баланс у модели выглядит для клиента так же, как «агент сломался».

## Google: обязательно перевести приложение в Production

В режиме **Testing** Google отзывает refresh-токен **через 7 дней** — и не сообщает об этом, пока агент не попробует им воспользоваться. Отсюда правило поставки:

1. Google Cloud Console → проект клиента → **APIs & Services → OAuth consent screen** (в новой консоли: Google Auth Platform → Audience).
2. **Publishing status → Publish app → In production.**
3. Проверка приложения Google не нужна.
   - **Что увидит клиент:** при авторизации экран «Google hasn’t verified this app» → «Advanced» → «Go to … (unsafe)». Предупредить клиента заранее: это его собственное приложение, а не чужое.
   - **Ограничения:** без проверки — до 100 пользователей; для одного клиента этого достаточно.
   - **Scope Gmail и Drive** (restricted) в Production без проверки тоже работают. Этот же экран-предупреждение — всё, что нужно.
4. **Если у клиента Google Workspace** (корпоративный домен), лучше User type = **Internal**. Тогда нет ни предупреждения, ни 7-дневного лимита.
5. **После смены статуса авторизоваться заново.** Токен, выданный в режиме Testing, всё равно умрёт по старым правилам.

## Ежедневная проверка (ставится в каждую поставку)

Скрипт `scripts/vps/integrations-check.py`:
- работает без LLM, только на stdlib;
- юниты systemd `--user`: `scripts/vps/systemd/hermes-integrations-check.{service,timer}`.

Что делает:
- Google — обновляет токен, не перезаписывая файл. Предупреждает, когда токену 5,5+ дней, а приложение в Testing (`HC_GOOGLE_MODE=testing`, по умолчанию).
- Todoist — запрос к API ключом.
- VK — `groups.getById` ключом сообщества.
- Timeweb — запрос на 1 токен к основной модели. Это ловит и битый ключ, и пустой баланс.
- reg.cloud — `/models`.
- Пишет владельцу в VK (`VK_HOME_CHANNEL`) **только при изменении состояния**: сломалось → что именно и что сделать; починилось → «снова работает». Состояние хранится в `~/.hermes/integrations-check.json` (600).
- Запуск: 00:30 UTC (03:30 МСК, за час до сводки) и 09:00 UTC.

Установка:

```bash
install -m 755 integrations-check.py ~/.local/bin/
install -m 644 hermes-integrations-check.{service,timer} ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now hermes-integrations-check.timer
python3 ~/.local/bin/integrations-check.py --dry-run        # посмотреть результат, ничего не отправлять
python3 ~/.local/bin/integrations-check.py --force-notify   # проверить, что уведомление доходит в VK
```

После перевода Google в Production — `HC_GOOGLE_MODE=production` в `.env`. Тогда предупреждения о возрасте токена отключаются.

## Сценарий переподключения (приёмка поставки)

Проверяем на приёмке, а не когда сломается само:

1. **Ломаем:** отзываем доступ Google на myaccount.google.com/permissions (или сбрасываем ключ Todoist).
2. **Ждём результат:**
   - `integrations-check.py` присылает в VK «❌ Google… Что сделать: …»;
   - сводка не падает, а честно пишет «календарь недоступен».
3. **Переподключаем** по таблице выше. Засекаем время: цель — до 5 минут для владельца.
4. **Проверяем:** следующий прогон присылает «✅ снова работает», агент читает календарь.

Клиенту на старте говорим прямо:
- «раз в несколько месяцев Google может попросить войти заново — агент сам напишет, что нужно сделать»;
- «если кончатся деньги на модели, агент напишет до того, как перестанет отвечать».

## Что ещё не закрыто

- **Переподключение Google сейчас требует нас.** Авторизация идёт через `google_api.py` / `setup.py` навыка google-workspace, а это шаги в терминале. Нужен сценарий, который клиент проходит сам по ссылке:
  - вариант 1 — агент присылает ссылку авторизации в VK и принимает код ответом;
  - вариант 2 — подключения в веб-интерфейсе 0.23 (`manage_connections`, hosted connectors). Не проверено.
- **Баланс Timeweb виден только как отказ.** Заранее, до нуля, не предупреждаем. Нужен API баланса или автопополнение.
