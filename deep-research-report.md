# Резюме

Для надёжной долгосрочной работы Hermes Agent рекомендуется развернуть его на Linux-сервере (VPS или домашнем сервере) под управлением systemd или в контейнере Docker. Простая установка через Python+venv подойдет для отладки, но для production лучше использовать сервис (systemd) или контейнер для автоматического перезапуска и изоляции. Структура `~/.hermes/` (конфиг, ключи, скилы, память, журналы) должна храниться под версионным контролем и регулярно бэкапиться. По умолчанию полезно включить базовые инструменты (веб-поиск, терминал, работа с файлами, браузер) и отключить рискованные (прямой код, голос), согласовывая их использование через запросы подтверждения. Для голосового режима рекомендуем локальную STT (faster-whisper) и бесплатный TTS (Edge TTS) с возможностью переключения на ElevenLabs/OpenAI для качества. В целом, **долгоживущий агент** стоит запускать от непривилегированного пользователя, защищённого firewall’ом, с watchdog-перезапуском, логированием в journald и резервными копиями. Используйте git-распределение («**Profile Distribution**») для версионного хранения конфигурации и навыков (skills)【17†L74-L83】. Ниже – подробное руководство по каждому аспекту.

## 1. Развёртывание Hermes

- **Python + venv:** самый простой способ – `pip install hermes-agent` в виртуальном окружении. Удобен для экспериментов, но требует ручного управления процессом (нет авто-перезапуска) и менее портируем.  
- **Docker / Docker Compose:** официальное Docker-изображение [`nousresearch/hermes-agent`](https://hub.docker.com/r/nousresearch/hermes-agent) упрощает переносимость. В контейнере легче обеспечить изоляцию и однородную среду: один и тот же образ запускается где угодно【58†L69-L74】. Минус – больше накладных расходов (размер ~1.1 GB, настройка монтирования томов). Подойдёт, если вы планируете инфраструктуру на контейнерах.  
- **systemd-сервис:** считается лучшей практикой для долгоживущих агентов. Пример unit-файла запуска Hermes как системной службы (non-root) приведён ниже. Он настроен на автоперезапуск при сбоях (`Restart=on-failure`), задержку между попытками (`RestartSec=10`) и ограничение ресурсов (2GB RAM, 2 CPU)【56†L219-L228】. Такой сервис подключается к `journalctl` и хранит логи (см. ниже).  

```ini
[Unit]
Description=Hermes Agent Gateway
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=hermes
Group=hermes
WorkingDirectory=/home/hermes
Environment="HOME=/home/hermes"
Environment="PATH=/home/hermes/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
ExecStart=/home/hermes/.local/bin/hermes gateway start
Restart=on-failure
RestartSec=10
StandardOutput=journal
StandardError=journal
SyslogIdentifier=hermes
MemoryMax=2G
CPUQuota=200%
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=read-only
ReadWritePaths=/home/hermes/.hermes

[Install]
WantedBy=multi-user.target
```

- **VPS / домашний сервер:** Любой современный Linux (Debian/Ubuntu LTS, CentOS, Alpine) подойдёт. Обычно запускают на x86- или ARM-серверах. Преимущество VPS – статический IP, доступность из интернета (для Telegram/Discord gateway). Без привилегий роутера можно использовать Dynamic DNS. На Windows или macOS Hermes теоретически работает, но для 24/7 стабильности всё же рекомендуем Linux. Например, «Hermes не привязан к ноутбуку» и может жить на «$5 VPS»【58†L69-L74】.

**Рекомендация:** ставьте Hermes под непривилегированным пользователем Linux на стабильной ОС (Debian/Ubuntu). Заводите systemd-сервис с автоперезапуском. Опционально: контейнер Docker или Docker Compose (особенно если нужны изоляция или многоконтейнерная связка). Для локальных тестов можно пользоваться venv, но продакшену служба предпочтительнее.

## 2. Стабильная работа 24/7

Чтобы агент всегда работал и сам поднимался после сбоев:

- **systemd-сервис:** как показано выше. Ключи: `Restart=on-failure`, `RestartSec=10`【56†L219-L228】, чтобы при падении сервис поднимался с небольшой задержкой. `After=network-online.target` гарантирует, что сеть поднялась до старта. Ограничьте ресурсы (`MemoryMax`, `CPUQuota`) и включите аппаратное ограничение привилегий (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=read-only`)【56†L226-L231】. Это предотвращает доступ к остальным частям системы в случае уязвимости.  
- **Автозапуск при перезагрузке:** `systemctl enable hermes` (команда `systemctl enable hermes`) обеспечит запуск после ребута. Права и `HOME` настроены в unit-файле.  
- **Политика перезапуска:** `Restart=on-failure` перезапустит агент при любом ненулевом коде выхода. Можно добавить `RestartSec=10` (см. пример), чтобы избегать «брутфорса» провайдера при частых падениях【56†L219-L228】.  
- **Watchdog/Recovery:** дополнительно можно настроить systemd Watchdog или использовать внешний скрипт (например, `hermes gateway restart` при закрытии). Базовая защита – наличие systemd уже обеспечивает автоматическую перезагрузку.  
- **Логирование:** вывод Hermes (стандартный и ошибки) направлен в systemd/journald (в примере выше). Для просмотра используйте:
  ```bash
  journalctl -u hermes -f             # в реальном времени
  journalctl -u hermes -p err         # последние ошибки за час
  ```  
  По умолчанию journald аккумулирует и ротацирует логи. При желании явно ограничьте объём через `/etc/systemd/journald.conf` (напр. `SystemMaxUse=200M`)【56†L256-L264】.  
- **Лог-файлы Hermes:** Hermes также пишет локальные логи в `~/.hermes/logs/` (ошибки, gateway.log). Они содержат красноречивую отладочную информацию (с автоматически замаскированными секретами)【42†L69-L72】. Следите за ними по мере необходимости.   
- **Грейсфул рестарт:** команда `/quit`, `/exit` закрывает агента с очисткой. Для перезагрузки конфигурации можно использовать `hermes gateway reload` или перезапустить сервис.   
- **Пример перезапуска:**
  ```bash
  sudo systemctl stop hermes
  hermes update  # обновляем бинарь, если нужно
  sudo systemctl start hermes
  ```
  Стандартного механизма «горячего» обновления нет, поэтому новую версию после `hermes update` принимаем перезагрузкой сервиса【56†L298-L305】.  

## 3. Безопасность

### На уровне системы

- **Отдельный пользователь:** заведите на системе отдельную учётную запись (например `hermes`), под которой запускается агент (см. `User=` в unit-файле). Не запускайте Hermes от root. Это ограничит ущерб при взломе.  
- **Права доступа:** папка `~/.hermes/` (и внутри файлы `config.yaml`, `.env`, ключи) должна быть доступна только этому пользователю (600 или 700). SSH-ключи и API-ключи храните вне репозиториев, в `.env` под защитой ОС.  
- **SSH-харденинг:** отключите вход для root, используйте аутентификацию ключами. Можно перенести SSH на нестандартный порт. Инсталляция Hermеs не влияет на SSH, но системно следуйте руководствам по безопасному SSH.  
- **Firewall:** открывайте на сервере только порты, необходимые для внешних шлюзов (например, порт Telegram HTTP-запросов, если нужен webhook, или порты 22/80/443 и т.п.). Например, UFW или iptables можно ограничить по адресам.  
- **Обновления:** держите систему и сам Hermes обновлёнными (`hermes update`). Если критические уязвимости в зависимостях или ядре – это устранит многие риски.  

### Внутри Hermes

- **Исполнение команд:** по умолчанию Hermes проверяет опасные shell-команды через “Dangerous Command Approval”【32†L113-L121】. Режим **manual** («ручной») требует подтверждения пользователя для подозрительных операций. Режим **smart** позволяет LLM (Claude/OpenAI) фильтровать. Режим **off** или `/yolo` (YOLO mode) отключает проверки – НЕ рекомендуется в незнакомой среде【32†L113-L121】. При cron-запусках опасные команды можно блокировать (`cron_mode: deny`).  
- **Сэндбоксинг:** используйте изолированный backend для терминала. Наилучший уровень безопасности даёт Docker или контейнеры Modal/Daytona: тогда по умолчанию **все** проверки опасных команд пропускаются, потому что контейнер служит барьером【38†L465-L474】. Если стоит `terminal.backend: local`, то агент ходит по вашей системе и нужны approval prompts. Docker-бекенд запускается с кап-дропами и другими флагами безопасности【38†L404-L413】 (см. таблицу сравнения в конце раздела Security).  
- **MCP и внешние инструменты:** удалённые серверы инструментов (MCP) запускают собственные subprocess’ы. Hermes отделяет их окружение (фильтрует переменные), но любая команда через MCP по сути исполняется «где-то ещё». Не подключайте сомнительные MCP-серверы и внимательно читайте их манифест (инструменты) перед добавлением【9†L14-L23】【9†L24-L30】.  
- **Борьба с инъекциями:** Hermes сканирует подключаемые файлы и генерируемые команды на признаки инъекций (специальная подсистема Tirith) и выводит предупреждения. Например, директива `[[as_document]]` в ответе заставит бот прислать файл как документ, а не показ; это помогает избежать утечек медиа. Также используйте `skills` и `toolsets` как замки: если навык или инструмент не подключен, агент не увидит его в подсказке.  
- **Секреты:** API-ключи хранятся в `~/.hermes/.env` (по стандарту используются HTTPS-паттерны). По умолчанию Hermes выводит их в логи как `***`. Опция `redact_secrets: true` в config.yaml дополнительно вырезает ключи из результатов инструментов【44†L29-L37】. Никогда не передавайте секреты или токены незащищённо в чате.  

*Итого:* минимум спец-настроек: запускать Hermes под непривилегированным юзером, не включать Docker backend локально без надобности, держать требуемые ключи в защищённом файле `.env`, использовать approval-подтверждения. В production-режиме целесообразно контейнеризовать агента или запускать его под `exec`-сервисом, чтобы система брала на себя защиту (как показано выше【56†L226-L231】【38†L465-L474】). Не давайте агенту root-доступ и строго определяйте, какие пользователи мессенджера могут с ним общаться (см. авторизацию ниже).

## 4. Настройка Hermes

- **config.yaml и .env:** все настройки вне секретов лежат в `~/.hermes/config.yaml`, а API-ключи, токены ботов, пароли – в `~/.hermes/.env`【42†L63-L72】【42†L105-L109】. Команда `hermes config set KEY VAL` автоматически определит, куда сохранить: ключи – в .env, остальные параметры – в config.yaml.  
- **Основные параметры:** через `hermes setup` задайте провайдеры LLM и инструменты. Например, `hermes setup --portal` (если есть Nous Portal) сразу настроит модель и даст доступ к четырём главным инструментам (поиск, генерация, TTS, браузер)【42†L55-L62】. Либо вручную `hermes model` для выбора модели и прописывайте ключи (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY` и т.д.) в .env.  
- **Профили:** если нужно несколько агентов с разными конфигами, используйте `hermes profile create <name>`. Тогда в `~/.hermes/profiles/<name>/` получится свой набор `config.yaml`, `SOUL.md`, `skills/` и т.д. Это изолирует настройки. Команды `hermes -p <name> <command>` переключают профиль.  
- **SOUL.md (линейка личности):** основной системный промпт (личность агента) лежит в `~/.hermes/SOUL.md` (или в профиле). Редактируйте его, чтобы задать «характер» бота. При необходимости можно переключить системный prompt командами (см. docs «Personality & SOUL»).  
- **Инструменты:** список инструментов (`tools & toolsets`) задаётся через `hermes tools`. Например:
  ```bash
  hermes chat --toolsets web,terminal,browser,skills
  hermes tools list
  hermes tools disable vision image_gen
  ```
  По умолчанию стоит набор базовых тулсетов: `web`, `search`, `terminal`, `file`, `browser`, `vision`, `image_gen` и др.【31†L80-L89】【31†L125-L133】. Подберите под себя – например, если не нужен аудио, уберите `tts` или `microphone`. Всегда держите выключенными любые `terminal` команды для непривилегированного или подозрительного кода.  
- **Провайдеры поиска:** `web_search` может использовать разные backends: FireCrawl (default), Parallel, Tavily, Exa. В `config.yaml` задайте `web.backend: firecrawl` или нужный. Пример конфигурации:
  ```yaml
  web:
    backend: firecrawl   # или parallel, tavily, exa
  ```
  Не забудьте прописать ключи (`FIRECRAWL_API_KEY` и т.п. в .env)【50†L83-L92】. Поиск можно переключать и из чата командой типа `/toolsets search`.  
- **MCP-сервера:** чтобы подключить внешний MCP, добавьте блок в config.yaml или используйте CLI `hermes mcp install`. Пример ручной настройки в config.yaml:
  ```yaml
  mcp_servers:
    - name: codeclub
      url: https://mcp.codeclub.dev
      tools: [paste, grep]
  ```
  После `hermes gateway start` агент автоматически достанет манифест инструмента. Можно установить заранее через `hermes mcp install codeclub`【9†L14-L23】【9†L24-L30】. В config файле MCP-сервера хранятся в `mcp.json`.  
- **Skills и навыки:** см. раздел 7 ниже – навыки загружаются из папки `~/.hermes/skills/`. Чтобы расширить функционал, подключайте навыки через `hermes skills install` или добавляйте свои `SKILL.md` в эту директорию.  
- **Память:** ограничьте `memory.max_tokens` или `memory.num_snippets` в config.yaml, чтобы не разрастался MEMOry и не нагружал контекст. По умолчанию Hermes сохраняет всё в `~/.hermes/memories/MEMORY.md` и `USER.md`. При долгой работе стоит перезагружать сессии (`/compress`, `/new`) и при необходимости чистить старые.  
- **Журнал и режимы отладки:** в `config.yaml` можно включить `log_level: debug` для подробностей в `~/.hermes/logs/`. Параметр `tirith_enabled: true` включает детектор нежелательных команд【44†L29-L37】. Опция `errors_to_telegram: true` (если есть телеграм-бот) пошлёт критические логи напрямую вам.  
- **Пример хорошей конфигурации (config.yaml):**  
  ```yaml
  provider: openai
  model: gpt-4o
  temperature: 0.5

  tools:
    terminal:
      backend: docker
      docker_image: "nikolaik/python-nodejs:python3.11-nodejs20"
      env_passthrough: []
    web:
      backend: firecrawl
    discord:
      token: ${DISCORD_TOKEN}
      allowed_users: [1234567890]
    ssh:
      host: example.com
      user: deploy
      key: ~/.ssh/id_rsa

  approvals:
    mode: manual
    timeout: 60
  ```
  Обязательно запишите `token` бота и сервис-ключи (как `${DISCORD_TOKEN}`) в файл `~/.hermes/.env`. Всего из обязательных – как минимум ключи LLM и необходимых тулов.  

В результате получится система, где `~/.hermes/` хранит: `config.yaml` (настройки), `.env` (ключи), `SOUL.md`, `skills/`, `memories/`, `sessions/`, `cron/`, `logs/`【42†L63-L72】. Главное – сохранять версионность конфигов (см. раздел 8) и не нарушать структуру.

## 5. Голос: STT и TTS

Hermes поддерживает полноценное голосовое общение. Есть локальные и облачные опции.

- **Распознавание речи (STT):**  
  - *Local:* быстрое и бесплатное решение – `faster-whisper` (Whisper на CPU/GPU). Достаточно установить его, и голос будет распознаваться offline (ключи не нужны)【45†L152-L160】【48†L539-L544】. Вывод – точность **хорошая**, задержка зависит от CPU (до ~1 с на короткой записи).  
  - *Cloud:*  
    - **Groq Whisper:** бесплатный быстрый API с низкой латентностью (~0.5–1 с) и неплохим качеством【48†L539-L544】. Имеется бесплатный теневой тариф (до 20 минут голоса в минуту).
    - **OpenAI Whisper API:** точность высокая, но платно (кол-во токенов). Задержка ~1–2 с【48†L539-L544】.  
    - **xAI Whisper:** поддерживается через `XAI_API_KEY` (требует аккаунта), сравнимо с OpenAI.  
  - *Приоритет:* Hermes сам подбирает STT в порядке **локально → Groq → OpenAI**【48†L539-L544】. Если установлен faster-whisper, он предпочтителен (в описании – «priority local > groq > openai»).  
- **Синтез речи (TTS):**  
  - *Edge TTS:* Microsoft Edge Voices через OpenAI Tool Gateway (по сути Azure TTS) – **хорошее** качество, бесплатный (на момент написания), задержка ~1 сек【48†L550-L554】. Не требует ключа (используется через Nous Portal или локальную обёртку). Обычно работает по-умолчанию без настроек.  
  - *ElevenLabs:* **отличное** качество речи, но платно (учёт по символам)【48†L550-L554】. API-ключ храните в `ELEVENLABS_API_KEY` в .env. Тормозит немного дольше (~2 с), но очень выразительно. Хороший выбор, если необходим натуральный голос.  
  - *OpenAI TTS:* неплохой голос (как у ChatGPT-4o), платно (`VOICE_TOOLS_OPENAI_KEY`), средняя латентность (~1.5 с)【48†L550-L554】.  
  - *NeuTTS:* локальный нейросинтез на CPU (через `neutts` Python-модуль). Без ключей, но качество чуть хуже (зависит от CPU/тяжёлых моделек)【48†L550-L554】. Можно использовать как резерв.  
  - *Рекомендации:* Для приватности лучше сначала ставить локальные (faster-whisper + Edge TTS/NeuTTS) – ключи никуда не отдаются. Если готов платить или нужна супер-натуральная речь – ElevenLabs (в паре с Whisper) даст лучший результат.  

- **Сравнение (пример):** TTS-провайдеры в виде таблицы【48†L550-L554】:  
  | Провайдер  | Качество | Стоимость | Латентность | Ключ нужен |
  |------------|----------|-----------|-------------|------------|
  | Edge TTS   | Хорошее  | Бесплатно | ~1 с        | нет        |
  | ElevenLabs | Отличное | Платно    | ~2 с        | да         |
  | OpenAI TTS | Хорошее  | Платно    | ~1.5 с      | да         |
  | NeuTTS     | Хорошее  | Бесплатно | зависит от CPU/GPU | нет |

- **Настройка ключей:** добавьте в `~/.hermes/.env`:  
  ```
  # STT
  GROQ_API_KEY=...             # (Groq Whisper)
  VOICE_TOOLS_OPENAI_KEY=...   # (OpenAI Whisper & TTS)
  # TTS
  ELEVENLABS_API_KEY=...
  ```  
  Если установлен faster-whisper, то настраивать ничего не нужно для STT【45†L152-L160】. При использовании Edge TTS/NeuTTS ключи не требуются.  
- **Линейка провайдеров:** подробная сводка в документации (см. «Voice & TTS» в Integrations и Voice Mode).  

В **локальной установке** рекомендуем: **faster-whisper** (стоит на все платформы) и **Edge TTS** (или NeuTTS) для полноценного “привычного” звука без внешних вызовов. В **cloud-сценарии** (сервер с ключами) – **Groq Whisper** + **ElevenLabs** для максимального качества/скорости. По умолчанию Hermes будет использовать «наиболее быструю опцию с доступным ключом» (см. сравнение【48†L539-L544】【48†L550-L554】).

## 6. Поиск, инструменты и интеграции

Hermes может пользоваться множеством встроенных инструментов и внешних сервисов:

- **Веб-поиск:** встроенный тул `web_search` (и `web_extract`) поддерживает несколько backends【50†L78-L87】. По умолчанию – FireCrawl. В конфиге задаётся `web.backend: firecrawl|parallel|tavily|exa` и ключи (`FIRECRAWL_API_KEY`, и т.д.). Пример:  
  ```yaml
  web:
    backend: firecrawl
  ```  
  Чтобы переключить источник поиска, используйте `hermes tools` или в командной строке `hermes chat --toolsets "search,web"`. Ссылки можно получить через `.  
- **Браузер:** есть встроенный инструмент `browser` (Chrome через CDP или облачные браузеры). Опции – Browserbase (управляемый облачный браузер), Browser Use (другой облачный), локальный Headless Chrome (через `agent-browser`), либо подключение к уже запущенному Chrome (`/browser connect`)【50†L97-L106】. Это удобно для автоматизации действий на сайте (клики, формы). Обычно включают при обработке web-задач.  
- **Системные инструменты:** `terminal` (команды shell), `read_file/patch`, `process`, `execute_code` – позволяют читать/писать файлы, запускать процессы, выполнять Python/код. По умолчанию включены, но в конфиге можно отключить ненужные. Пользователю видно, какие команды агент планирует выполнить, и он подтверждает опасные (при `approvals`). Если доверяете, можно переключиться на YOLO-режим (`/yolo`).  
- **Интеграции MCP:** описаны в разделе “MCP” выше. Через MCP можно «подцепить» GitHub, базы данных, API «из мира» как инструменты. Полезно по умолчанию: например, MCP сервер GitHub (HackerNews/Mosaic) для поиска кодов или Integrations. Подключайте MCP-сервера через `hermes mcp install` и доверяйте только проверенным.  
- **Поисковые боты (X, Telegram и др.):** встроены инструменты для X (Twitter) поиска (`x_search`), а также фильтры для Telegram, Discord и др. их часто включают по умолчанию при настройке `hermes gateway`. Список поддерживаемых платформ – >25 (Telegram, Discord, Slack, WhatsApp, Signal, Email, SMS и т.д.)【50†L153-L163】. Каждая требует своего ключа/токена в `.env`.  
- **Voice & TTS:** интеграции приведены выше, также упомянуты в интеграциях (см. таблицу provider'ов【50†L115-L123】).  
- **UI для инструмента:** никакого отдельного «GUI» нет. Все настройки делаются через конфиг/CLI. Однако можно рекомендовать добавить в интерфейс явное раскрытие готовых навыков/инструментов (`/skills`, `/bundles`) или интерактивное включение. 

**Рекомендации по умолчанию:** включите web-поиск, терминал/файловую систему и браузер. Если нужны, активируйте `vision` и `tts`. Остальные – по задаче. Для безопасности отключайте вещи типа `process.send_keys` (remote shell в браузере) или механизмы прямой отправки сообщений без явного согласия. Для передачи инструментов (например MCP) выдают «открытый» доступ со сканированными манифестами – следите за trust-level'ами (официальное/community). 

## 7. Skills и расширение агента

**Навыки (skills)** – текстовые описания алгоритмов, доступные через слеш-команды. 

- **Формат и каталог:** Навыки хранятся в `~/.hermes/skills/` (по категориям)【26†L293-L302】. Каждый – папка с `SKILL.md` и опциональными `scripts/`,`templates/` и т.д. В файле есть метаданные (название, описание, версия, тэги) и основные разделы («When to Use», «Procedure», «Verification»). Пример метаданных:
  ```yaml
  name: my-skill
  description: Краткое описание
  version: 1.0.0
  platforms: [linux, macos]
  metadata:
    hermes:
      tags: [python, automation]
      category: devops
      requires_toolsets: [terminal]
  ```
  Этот формат описан в документации【27†L117-L125】. Навык автоматически становится слеш-командой `/my-skill` в чате.  
- **Установка:**  
  - **Официальный репозиторий (Skills Hub):** `hermes skills browse|search` показывает доступные навыки (например, из каталога skills.sh, Marketplace Claude и др.). `hermes skills install <source>/<repo>/<path>` подтягивает навык с GitHub или рынка. Например: `hermes skills install official/security/1password`.  
  - **Прямой URL:** `hermes skills install https://example.com/SKILL.md`.  
  - **Локальные (самописные):** просто создайте папку с вашим `SKILL.md` в `~/.hermes/skills/<category>/`. Агент «увидит» этот навык после перезапуска сессии или команды `/reset`.  
  - **Удаление/откат:** `hermes skills uninstall <name>` удаляет ненужный навык (см. встроенные команды【24†L727-L737】). Есть и `hermes skills reset <name>`, чтобы откатить встроенный навык к оригиналу.  
- **Версионирование и CI/CD:** по умолчанию skills **не хранят версионную историю** (они в обычном каталоге)【16†L229-L237】. Поэтому рекомендуют:  
  - Завести `~/.hermes/skills/` как git-репозиторий и коммитить изменения (самое простое решение, предложено разработчиками)【16†L237-L244】.  
  - Либо включить `skills` в git-репозиторий **дистрибуции профиля** (Profile Distribution): тогда весь агент с навыками хранится в одном месте【17†L74-L83】.  
  - Можно также использовать `hermes skills publish` для публикации навыка на GitHub в виде Tap (привязка)【24†L740-L744】, а потом устанавливать через `skills install`.  
- **Sandboxing и разрешения:** навык сам по себе – просто документ с инструкциями. Он не исполняется как код, поэтому отдельной песочницы ему не нужно. Однако в SKILL.md можно указывать `requires_toolsets` (набор инструментов) и условные поля. Если навык требует, скажем, `terminal`, он не будет предложен, пока терминал включен. Таким образом можно управлять «правами» навыка.  
- **Bundles (наборы навыков):** полезно группировать несколько навыков под одним `/командой` (YAML в `~/.hermes/skill-bundles/`). Это удобно для комплексов задач (например `/release-prep` загружает сразу несколько нужных навыков)【24†L727-L737】【22†L670-L678】.  
- **Рекомендации по репозиторию:** хранить навыки в том же репозитории, что и конфиг агента, – хорошая практика, если агент делится с командой (через Git). Profile Distribution показывает структуру: папка `skills/` рядом с `config.yaml`, `SOUL.md` и т.д.【17†L74-L83】. Это обеспечивает версионирование и централизованную поставку. Минус – лишний overhead для обновлений (нужно переустанавливать навыки через git pull). Альтернативно, можно хранить только свои кастомные навыки в git (например в отдельном «tap»-репозитории) и устанавливать их при запуске.  

## 8. Бэкапы, миграции и структура проекта

**Структура `~/.hermes/`:** для удобства и резервных копий имеет смысл поддерживать её в понятном виде. Например:

```
~/.hermes/
├── config.yaml          # основная конфигурация агента
├── .env                 # секреты и API-ключи
├── auth.json            # OAuth учётные данные (Nous Portal и др.)
├── SOUL.md              # системный prompt (личность агента)
├── skills/              # навыки (SKILL.md и дополнительные файлы)
├── memories/            # постоянная память (MEMORY.md, USER.md)
├── cron/                # cron-задачи агента
├── sessions/            # хранимые разговоры (можно экспорты сессий)
├── logs/                # логи агента (errors.log, gateway.log)
└── backups/             # (по желанию) храним бэкапы/архивы
```

В **git-репозитории проекта** стоит хранить: `config.yaml`, `SOUL.md`, папку `skills/`, возможно `cron/` и `mcp.json`, то есть всё, что составляет дистрибутив агента (как в Profile Distribution【17†L74-L83】). Секреты (`.env`), ключи и сами данные агента (память, сессии) туда не коммитят. При необходимости бэкапа храните копию `~/.hermes/` (или используйте `hermes profile export`).

- **Backup стратегии:**  
  1. **hermes profile export/import:** встроенные команды для «быстрого бэкапа» всего профиля (config, skills, памяти, сессий) в tar.gz【53†L275-L283】【53†L290-L299】. Пример: `hermes profile export mybot -o mybot-backup.tar.gz`. Позже: `hermes profile import mybot-backup.tar.gz`.  
  2. **Git-репозиторий:** если используете Profile Distribution, обновления и история лежат в git. Это отлично подходит для «каталоговых» агентов, которым нужна версияция.  
  3. **Системный бэкап:** классическое копирование директории `~/.hermes/` (rsync, tar, слепок тома). Можно автоматизировать скриптом.  
  4. **Container snapshots:** если есть docker, можно снапшотить образ или volume.  
  Таблица сравнения:

  | Стратегия         | Что сохраняет                  | Плюсы                              | Минусы                        |
  |-------------------|--------------------------------|------------------------------------|-------------------------------|
  | `hermes export`   | config, skills, memory, сессии | Полный дамп профиля, прост в использовании【53†L275-L283】 | Не включает ключи (.env), нужно заново вводить ключи |
  | Git (Profile Dist)| всё, кроме секретов (config, skills, cron)【17†L74-L83】 | Версионирование, прозрачные diff’ы, единоразовая настройка | Не сохраняет данные/память |
  | Файловый копи-бекап | ВСЁ (включая .env, сессии, логи)  | Можно восстановить полностью (включая ключи) | Ручная настройка, большие объёмы |
  
- **Перенос между машинами:**  
  1. Установите Hermes (pip/docker) на новом сервере.  
  2. Копируйте `config.yaml` и `.env` (ключи) в `~/.hermes/`.  
  3. Скопируйте содержимое `skills/`, `memories/`, `sessions/` (если хотите продолжить историю).  
  4. Запустите `hermes config check` и `hermes config migrate` на новом месте – установщик подскажет недостающие параметры.  
  5. Запустите агента (через `hermes chat` или `gateway`). Он продолжит работу с прошлой памятью.  
- **Экспорт/импорт отдельных частей:**  
  - Конфигурацию можно сохранить в репозиторий или отдельный файл.  
  - Сессии: `hermes sessions export <session_id>` (в некоторых версиях) сохраняет историю в JSON.  
  - Prompt’ы (SOUL): просто копировать `SOUL.md`.  
  - Важный нюанс: команда `hermes profile export` не включает `auth.json` и `.env` (пользователь добавляет ключи вручную)【53†L328-L333】.

## 9. Мониторинг и отладка

- **Логи:** Hermes пишет служебные журналы. Их можно смотреть двумя способами:  
  1. **journald:** если запущен через systemd, вывод идёт в `journalctl`. Просматривать можно как выше (`journalctl -u hermes`). Это основной способ следить за ошибками (например, проблемы подключения к боту, сбои провайдера).  
  2. **Файлы:** в `~/.hermes/logs/` есть `errors.log` (критичные ошибки) и `gateway.log` (активность для Messaging Gateway)【42†L69-L72】. Эти файлы хранятся локально и пригодны для разбора инцидентов офлайн.  
- **Уведомления об ошибках:** если агент запущен на сервере, полезно настроить алерты: например, пересылать критические ошибки на почту или в чат администратора (механизм можно построить на cron или через уже существующие Telegram-уведомления при падении). В документации пока нет встроенного мониторинга, но можно патчами добавлять webhook при ошибках.  
- **Диагностика сессий:** Hermes сохраняет все диалоги в SQLite (`~/.hermes/state.db`). Чтобы узнать, что происходило:  
  - `hermes sessions list` – покажет все сохранённые сессии.  
  - `hermes sessions resume <name|id>` – вернёт историю чата в CLI.  
  - `hermes sessions search <ключевое слово>` – позволит быстро найти упоминание в любом чате.  
  - Если нужно «переиграть» сессию, просто откройте её снова командой `hermes --continue` или `hermes resume`.  
- **Диагностика состояния:** `hermes profile show <name>` выведет текущее состояние профиля (какой путь, модель, статус gateway, кол-во skills и т.д.)【53†L225-L233】. Это помогает убедиться, что агент запущен и конфиг валиден.  
- **Отладочные флаги:** для экспериментов можно поднять логирование до DEBUG: в config.yaml `logging.level: debug`. Тогда в `~/.hermes/logs/` будут подробные трейсы. Если есть утечка памяти или неизвестная ошибка, это даст зацепку.  
- **Быстрое восстановление:** при сбое часто помогает перезапустить сервис (`systemctl restart hermes`) или командой `hermes gateway start`. В крайнем случае можно откатиться на предыдущую версию через `hermes update`. Перед этим убедитесь, что все сессии уже сохранены (`/quit`).  
- **Watchdog:** как дополнение, можно завести внешний скрипт или systemd-таймер, который раз в сутки проверяет, работает ли Hermes (например, выполняя какой-то лёгкий `curl localhost:port` или проверяя статус `systemctl`). В случае «упал – поднять» / отправить уведомление. Это повышает надёжность.  

## 10. Итоговая рекомендация

Если бы я настраивал Hermes как долгоживущий агент, я бы сделал так:

- **ОС:** лёгкая и стабильная Linux-система (например, Ubuntu 24.04 LTS или Debian 12) на VPS. Я бы создал пользователя `hermes` и дал ему только свою домашнюю папку (жёстко ограничил права).  
- **Установка:** использовал бы официальное Docker-изображение (кроме случаев с GPU) или установку через pip в venv, но обязательно запустил бы как systemd-сервис. Таким образом Hermes работает в фоне и перезапускается системой. В примере выше (п.2) сервис настроен корректно【56†L219-L228】.  
- **Безопасность:** выбрал бы `terminal.backend: docker` для команд, чтобы всё выполнялось в контейнере с кап-дропами【38†L404-L413】. Установил бы `approvals.mode: manual` (с подтверждением) на продакшене【32†L113-L121】. Firewalld/UFW блокировал бы ненужные порты. SSH – ключи, отключил root. В docker-compose (если используется) повесил бы лимиты ресурсов.  
- **Конфигурация:** заполнил `config.yaml` и `.env` через `hermes setup --portal`, чтобы быстро получить настройки. В приоритете – HTTPS-провайдер (Nous Portal или OpenAI) и базовые инструменты. Default убрал всё лишнее (`process`, `send_email` и т.п.) через `hermes tools`.  
- **Навыки:** настраивал бы агента через дистрибуцию (репозиторий): создал бы папку `my-agent/` с `distribution.yaml`, `SOUL.md`, `config.yaml`, `skills/` и т.д. Это позволило бы version control через git (см. профиль-рекомендацию【17†L74-L83】). Хранил бы редкие навыки вместе с проектом в git, а стандартные – ставил через `hermes skills`.  
- **Голос:** для личного использования установил бы `faster-whisper` (STT) и настроил NeuTTS или Edge TTS (TTS) для оффлайн-режима. Если бы развернул на сервере с хорошим интернетом, добавил бы ключи ElevenLabs и OpenAI.  
- **Инструменты:** включил бы web-поиск, терминал, filesystem и браузер. XAPI (Twitter), Email, SMS и т.д. – по потребности. Настроил основную коммуникацию через Telegram (список разрешённых пользователей в `.env`). При падении агента – оповещение в Telegram.  
- **Бэкапы:** настроил бы ежедневный экспорт профиля (`hermes profile export myagent-$(date).tar.gz`) и периодический пуш репозитория с конфига. Также активировал journald rotation (`SystemMaxUse=100M`) на VPS.  
- **Мониторинг:** использовал `systemctl status hermes` и `journalctl -u hermes` для логов. При любых непонятках – `hermes sessions list` и `hermes sessions resume` для просмотра последних диалогов. В критических случаях включал `hermes config set logging.level debug`.

Такой подход даст высокую надёжность, безопасность и управляемость: агент автоматически стартует после сбоев, хранит свои данные отдельно от кода (в профиле), легко обновляется, а все ключевые аспекты конфигурируются через файлы/команды. UX-поток использования также будет предельно простым: один сервис (гейтвей) работает постоянно, CLI доступен для ручного взаимодействия, а веб/голосовые «фронты» (Telegram/Discord) подключены через него. Это сочетание даёт удобство использования и продакшен-надёжность.

**Приоритетные улучшения UX (со сложностью):**

- **Автоматический веб-интерфейс администрирования** *(High)* – единая панель для установки навыков, настроек и логов (со связью с `hermes` API) вместо чистого CLI. Позволит не доверять терминалу пользователям.  
- **Интерактивное управление MCP-серверами и инструментами** *(Medium)* – удобный CLI (или TUI) для просмотра/включения/отключения MCP и тулов (ISSUE #690). Сейчас приходится менять YAML вручную или переустанавливать.  
- **Версионирование и откат навыков** *(Low)* – сделать `~/.hermes/skills/` git-репо (коммитить при изменениях) или встроенный `hermes skill rollback`. Предотвратить silent failure при порче SKILL.md【16†L229-L237】.  
- **Улучшенный onboarding** *(Medium)* – пошаговый мастера-сценарий: создание профиля, настройка модели/ключей, выбор базовых инструментов, первый чат. Снижение порога входа.  
- **Просмотр и анализ логов из CLI/WebUI** *(Low)* – команда `hermes logs [--level error]`, поиск по сессиям/туллам. Сейчас нужно вручную читать файлы/journal.  
- **Роль многопользовательского доступа** *(Medium)* – разграничить права (настройки/очистка памяти только для администратора, обычный пользователь – только чат). Можно через профили или расширенные allowlists/DM-пары【38†L320-L329】.  
- **Пример рабочего флоу (hermes skills install)**:
  ```mermaid

    User->>Hermes CLI: hermes skills install myrepo/my-skill
    Hermes->>Hub: Fetch skill from repo
    Hermes-->>User: Skill installed (ok)

    Hermes->>Agent: Load skill content, await `/my-skill` command
    User->>Hermes CLI: /my-skill Сделай X
    Hermes->>Agent: Execute skill procedure...
  ```
- **Пример потока MCP**:
  ```mermaid

  ```

Эти улучшения и рекомендации обеспечат **удобство** (простой старт, понятный интерфейс) и **управляемость** (отказоустойчивость, безопасность), что критично для «длинного» запуска агента. В конечном счёте Hermes должен «работать как сервис»: надежно, автоматически и с минимумом ручного вмешательства, при этом оставляя гибкость настройки через файлы и команды. Именно так я бы настроил Hermes для себя – ориентируясь на лёгкий перенос, безопасность и удобство мониторинга, сохраняя возможность расширять функционал навыками и инструментами.
